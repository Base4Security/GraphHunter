# A5 — Libro attribution audit (figures, datasets, `@book-snippet` markers, refs.bib)

**Date:** 2026-05-26
**Method:** Walked `docs/libro/` and the repo's `@book-snippet` markers in source files; ran `tools/extract-listings.py --check`; manually diffed in-tree TS listings against their referenced source files; spot-checked `refs.bib` completeness; scanned for external image files and dataset mentions.
**Worker:** unit-12
**Base commit:** 99fb150

## Summary

2 findings: 0 P0, 0 P1, 2 P2. The libro is in good shape for v1.0.0 attribution:
all 74 figures are TikZ-generated (no external sourcing requires attribution),
all 36 Rust `@book-snippet` references resolve correctly via the autogenerated
listing pipeline, no external datasets are mentioned (the Cap 0 example dataset
is repo-generated and synthetic), and `refs.bib` (59 entries) covers the
SIMD/WCOJ/graph theory citations used in the body. The two findings concern
the TypeScript listings, which the autogenerator does not process — they are
hand-managed copies kept in-tree and have drifted slightly from the source.

## Findings

### F1 — `listings/mcp/hunt-run-tool.ts` body drifted from source

- **Severity:** P2
- **Axis:** docs
- **Front:** libro
- **Evidence:** `docs/libro/listings/mcp/hunt-run-tool.ts` (committed in-tree) diverges from `platform/mcp/src/tools/hunt/run.ts:21-45`, even though both files carry the same marker `@book-snippet:mcp/hunt-run-tool`. Concrete divergences: (a) the committed listing includes preceding `import` statements and the `input` schema declaration that are *outside* the marker block in source; (b) the `description` field text was rewritten/shortened (committed version: ~5 lines about self-contained replayable transcripts; source version: dense single-line description ending with "The legacy `enable_anomaly_scoring` latch is no longer load-bearing."); (c) the source has an explanatory comment block inside `execute()` referencing `apps/tauri/src-tauri/src/http/hunt.rs` and `platform/api/src/dto/v1/hunt.rs` that the committed listing omits.
- **Risk:** The book teaches readers about `defineTool` using a snippet that does not exactly match the live tool. Structure and field names are correct, but the description prose is no longer the one users see in `tools/list` responses, and the inline rationale comments are lost.
- **Fix action:** Either (a) regenerate the listing from the source marker — but `tools/extract-listings.py` currently only handles `.rs` files (see `SNIPPET_END = re.compile(r"//\s*@book-snippet-end\s*$")` and the `rglob("*.rs")` loop at line 63); extend the script to also process `*.ts`/`*.tsx`/`*.js` and remove the now-stale committed copy, OR (b) accept the listing is hand-managed and add a comment at the top of `docs/libro/listings/mcp/hunt-run-tool.ts` stating "hand-curated extract; resync if `platform/mcp/src/tools/hunt/run.ts` changes". Option (a) is preferable for v1.0.0 because it eliminates the drift class entirely.
- **Cost:** S (≤4h) — extending the extractor is ~30 LOC plus a test in `tools/test_extract_listings.py`; updating the Makefile target if needed.
- **Gate:** post-release
- **Owner suggested:** automatable

### F2 — `listings/mcp/tool-interface.ts` has no `@book-snippet` marker in source

- **Severity:** P2
- **Axis:** docs
- **Front:** libro
- **Evidence:** `docs/libro/parte4-superficies/35-mcp-tools.tex:275` runs `\inputminted{typescript}{listings/mcp/tool-interface.ts}` and the file `docs/libro/listings/mcp/tool-interface.ts` exists in-tree. The libro attributes the snippet at line 269 to `platform/mcp/src/lib/types.ts` and the file does contain `export interface Tool<I = unknown, O = unknown>` at line 71. However, **no `@book-snippet:mcp/tool-interface` marker exists anywhere in the repository** (`grep -rn '@book-snippet:mcp/tool-interface' .` returns nothing). The committed listing is a hand-edited compact rendering — it collapses `ToolCategory` from 13 separate string literals into a 3-line grouped form to fit the page, and inlines `ZodSchema` without importing it.
- **Risk:** Same drift class as F1: if `Tool<I, O>` evolves in `platform/mcp/src/lib/types.ts` (e.g. fields renamed, new required fields), the hand-authored listing will silently desync. The book will display an obsolete interface as canonical.
- **Fix action:** Add `// @book-snippet:mcp/tool-interface` / `// @book-snippet-end` markers around the `Tool<I, O>` interface in `platform/mcp/src/lib/types.ts:71-82` (or a comparable block), then either extract automatically (after F1's extractor extension lands) or copy the canonical block into the committed listing and document the linkage. Concretely: edit `platform/mcp/src/lib/types.ts` to add the markers, and resync `docs/libro/listings/mcp/tool-interface.ts` so the bodies match byte-for-byte.
- **Cost:** XS (≤1h) — single source-file edit + listing resync.
- **Gate:** post-release
- **Owner suggested:** tú

### Out of scope (noted for context)

- The libro itself is GPL-3.0 (same as the codebase). Quoting one's own GPL-3.0 code does not require additional attribution beyond the project license; the `\sourceref{...}` macros throughout the chapters provide the path-and-line pointer back to the authoritative source, which is the discoverability requirement.
- The `docs/libro/refs.bib` `@misc` URL entries link to external projects (HuggingFace candle, llama.cpp, MLC xgrammar, Microsoft llguidance) but those are bibliographic citations — no source code or text from those projects is reproduced verbatim in the libro.
