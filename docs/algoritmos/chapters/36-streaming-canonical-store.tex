\chapter{\emph{Streaming} como almacenamiento canónico}
\label{cap:streaming-canonical}

\begin{intuicion}
\textbf{Stage 2c part 2 entregado.} El \texttt{SpillableEdgeStore}
fue eliminado del árbol; el \emph{streaming backend} es el único
edge store. El matcher \emph{hot path}, los $\sim$50 readers
\emph{admin/aggregation/index-build}, y los cinco \emph{ingest
paths} (\texttt{add\_relation}, \texttt{add\_relations\_batch},
\texttt{replay\_relations}, \texttt{compact\_before},
\texttt{remove\_entities\_and\_relations\_by\_dataset}) leen y
escriben \texttt{streaming} directamente. Este capítulo era el
\emph{plano de obra}; ahora se mantiene como \emph{post-mortem
del plan} ---qué se hizo, qué riesgos se materializaron, qué
mitigaciones funcionaron--- con la narrativa original intacta
debajo.
\end{intuicion}

\begin{nota}[Lo que efectivamente shipped]
Tres commits secuenciales, cada uno bench-gated contra el
\emph{baseline} \code{pre-2c2}:
\begin{enumerate}
  \item \emph{Hot path migration} (5 call sites): \texttt{dfs\_match\_smart},
  \texttt{dfs\_match\_iterative}, \texttt{edge\_range\_sid},
  AMAC \emph{prefetch lookahead}, \texttt{amac\_step\_one\_edge}.
  Cada uno: \texttt{streaming.neighbors\_arc(sid)} \(+\)
  \texttt{guard.read()} \(+\) \texttt{guard.as\_slice()}.
  \texttt{parking\_lot::RwLock} reemplazó a
  \texttt{std::sync::RwLock} para que el par de read-guards
  per-frame quepa en el budget.
  \item \emph{50-consumer migration}: NLF, khop\_reach (build +
  delta), LFTJ, semijoin, Yannakakis, anomaly, analytics
  (8 sites), GNN bridge, matcher-ffi, platform/api.
  \item \emph{Rip-out del dual-write}: drop del field
  \texttt{edge\_store: SpillableEdgeStore}, drop del módulo
  \texttt{spill.rs} entero (1.2~KLOC), \texttt{streaming.clear()}
  para los rebuild paths, \texttt{push\_to\_streaming(\&CompactRelation)}
  helper compartido por los cinco ingest paths.
\end{enumerate}
\textbf{Bench (\texttt{hunt\_latency} vs \code{pre-2c2}):}
\(-29\)\% / \(-25\)\% / \(-26\)\% en 1K/10K/100K. \emph{Score-path}
mejoró \(-50\)\% a \(-55\)\% en todas las profundidades. Detalles
en \filepath{docs/perf/latex/cambios-perf-2026-04.tex}.
\end{nota}

\textbf{Plano de obra original (referencia histórica):} El resto
del capítulo conserva el plan tal como se escribió antes del
\emph{ship}. Los riesgos mencionados (regresión cache en
\texttt{Btree variant}, compatibilidad \emph{snapshot}/\emph{load})
se materializaron parcialmente: el \texttt{Btree variant} se
\emph{eliminó} en lugar de tunarse (preferimos \texttt{Vec}
contiguo + \texttt{partition\_point} para preservar el
\emph{prefetch lookahead} del matcher); la compatibilidad
\emph{save/load} sobrevivió intacta porque \texttt{add\_relation}
popula \texttt{streaming} en cada \emph{replay\_relations}.

\section{El problema}

Después de stage 2a (capítulo~\ref{cap:streaming-mirror}) cada
\texttt{add\_relation} hace dos writes:

\begin{enumerate}
    \item Al \texttt{edge\_store} canónico (\texttt{SpillableEdgeStore},
    eliminado en stage 2c part 2).
    \item Al \texttt{streaming} backend (per-vertex degree-adaptive,
    capítulo~\ref{cap:streaming-mirror}).
\end{enumerate}

\noindent
Memoria: las aristas viven en dos estructuras simultáneamente. Para
\(10^8\) aristas, eso es 6.4 GB \emph{repetidos} (32 B \(\times\)
\(10^8\) por edge\_store + similar por streaming). Costo de
insert: dos writes, dos cache lines tocadas.

El plan: \emph{una sola estructura} (streaming) que sirve a todos
los consumers, incluido el matcher hot path.

\section{Por qué no se hizo en stage 2a}

El matcher hot path consulta \texttt{edge\_store} via familia de
accessors: \texttt{get\_relations\_by\_sid},
\texttt{iter\_all}, \texttt{neighbors\_of},
\texttt{get\_compact\_relations}. Cada uno tiene semántica
\emph{sorted-by-timestamp} y \emph{binary-search-ready}. Migrar a
streaming significa re-implementar esa familia sobre el nuevo
layout \texttt{NeighborList}, que es \emph{degree-adaptive} (no
contiguo, no uniformemente sorted).

Tres call sites principales en
\filepath{core/graph-engine/src/graph.rs}:

\begin{itemize}
    \item DFS recursivo: itera \texttt{neighbors\_in\_window}.
    \item LFTJ-K\(_4\): construye trie sobre todas las aristas.
    \item Yannakakis: build\_bags itera por step.
\end{itemize}

\noindent
Cada uno asume el layout contiguo del edge\_store. Migración no
trivial.

\section{El plano: tres pasos}

\subsection{Paso 1: Adapter layer}

Crear una capa que mimica la API del \texttt{edge\_store} pero por
encima del streaming:

\begin{lstlisting}[language=Rust]
impl GraphHunter {
    pub fn neighbors_of_streaming(
        &self,
        sid: StrId,
    ) -> impl Iterator<Item = StreamEdge> {
        let snap = self.streaming.neighbors_snapshot(sid);
        match &*snap {
            NeighborList::Inline(arr) => arr.iter_owned(),
            NeighborList::Vec(v) => v.iter().cloned().collect(),
            NeighborList::Btree(bt) => bt.values().cloned().collect(),
        }
    }
}
\end{lstlisting}

\noindent
Sirve como \emph{drop-in replacement} de
\texttt{neighbors\_of}. El matcher hot path llama a la versión
adaptada en lugar de la legacy.

\subsection{Paso 2: Re-write del hot path}

Cada uso de \texttt{get\_relations\_by\_sid} se reemplaza por
\texttt{neighbors\_of\_streaming}. Los benches verifican parity
contra la versión legacy:

\begin{itemize}
    \item Target de regresión: \(< 10\%\) en
    \texttt{matching\_hops} y \texttt{hunt\_latency}.
    \item Si la regresión es mayor, revisar el layout de la
    \texttt{Vec variant}.
\end{itemize}

\subsection{Paso 3: Drop del \texttt{edge\_store}}

Con todos los consumers migrados, \texttt{edge\_store} queda como
estructura legacy mantenida sólo para
\texttt{session\_save}/\texttt{session\_load} (donde el formato
binario \texttt{GHS1} ya escribe \texttt{Relation}s en streaming).
La conversión \texttt{NeighborList $\to$ Relation} al guardar es
directa.

Eventualmente, eliminar el \texttt{edge\_store} entero: los
\texttt{Vec<Relation>} salen de \texttt{NeighborList}s flattened
on-demand.

\section{Beneficios esperados}

\begin{itemize}
    \item \textbf{RAM}: una sola copia de las aristas. Para 28~GB
    EVTX ($\sim$100~M aristas \(\times\) 32~B $\approx$ 3.2~GB
    ahorrado).
    \item \textbf{Latencia de \emph{insert}}: una sola escritura
    por \texttt{add\_relation} (en lugar de dos). Esperado
    $\sim$30\% más rápido en ingest throughput.
    \item \textbf{Concurrencia}: el streaming backend ya soporta
    readers concurrentes vía \texttt{ArcSwap}; los matchers de
    varios transports pueden correr simultáneamente. Hoy, el
    \texttt{edge\_store} requiere coordinación.
\end{itemize}

\section{Riesgos y mitigaciones}

\subsection{Regresión en matcher hot path}

El \texttt{edge\_store} usa \emph{contiguous Vec} sortado, perfecto
para \emph{cache prefetch}. La \texttt{NeighborList} tiene tres
variantes (\texttt{Inline}, \texttt{Vec}, \texttt{Btree}) con cache
behavior mixto. Especialmente la \texttt{Btree} variant: lookups
\(O(\log n)\) con cache misses por nivel.

\textbf{Mitigación}: benches contra \texttt{matching\_hops} y
\texttt{hunt\_latency} antes de cada commit. Si la regresión
\(> 10\%\), revisar:

\begin{itemize}
    \item ¿Es la \texttt{Vec variant} la que regresa? Optimizar
    cache layout.
    \item ¿Es la \texttt{Btree variant}? Aumentar el threshold
    de promotion (256 $\to$ 1024) para que menos vértices se
    vayan a \texttt{Btree}.
    \item ¿Es la \texttt{Inline variant}? Investigar
    branch prediction.
\end{itemize}

\subsection{Compatibilidad de \emph{snapshot}/\emph{load}}

El formato \texttt{GHS1} actual lee \texttt{Relation}s en
streaming y los inserta vía \texttt{add\_relation}. Eso sigue
funcionando porque \texttt{add\_relation} popula el streaming
backend sin más; el \texttt{edge\_store} legacy queda vacío en
\emph{post-load} y los matchers legacy paulatinamente migran a
streaming.

\textbf{Mitigación}: tests de round-trip
(\texttt{save $\to$ load $\to$ run\_hunt} produce same results
that pre-save).

\subsection{Cache behavior de NeighborList variants}

La preocupación más concreta. Hipergrafos \emph{scale-free} tienen
distribución bimodal: muchos vértices Inline (low degree, fits in
8), pocos hubs en Btree (high degree). El matcher típicamente
itera más por hubs (donde los paths se concentran), así que la
performance del \texttt{Btree} domina el bench.

\textbf{Mitigación}:
\begin{itemize}
    \item Profile real de los hunts cíclicos para entender qué
    fracción del tiempo se gasta en lookups Btree vs Inline.
    \item Si Btree domina: considerar layout más compacto (B+tree
    custom en lugar de \texttt{BTreeMap} stdlib).
    \item Plan B: mantener un \emph{indice secondario} para los
    hubs (ordered Vec on top of Btree). Más memoria, mejor cache.
\end{itemize}

\section{Cronograma estimado}

Stage 2c (canonical streaming): $\sim$3 semanas. La re-escritura
del matcher hot path toca 12+ call sites en
\filepath{core/graph-engine/src/graph.rs} más los benches; el
riesgo de regresión es lo que más empuja el timeline.

\section{Resumen}

\begin{itemize}
    \item Stage 2c: eliminar dual-write; streaming es source of
    truth, edge\_store on-demand.
    \item Tres pasos: adapter layer, re-write hot path, drop
    edge\_store.
    \item Beneficios: \(\sim 30\%\) menos RAM, \(\sim 30\%\) más
    rápido en insert, mejor concurrencia.
    \item Riesgos: regresión cache en hot path por NeighborList
    variants. Mitigación: benches en cada commit, threshold
    tuning, plan B con índice secundario.
    \item Cronograma estimado: $\sim$3 semanas.
\end{itemize}

\end{enumerate}
