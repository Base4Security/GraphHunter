\chapter{Finalización: \texttt{sort\_edges\_by\_timestamp}}
\label{cap:finalize}

\begin{intuicion}
Después de la última \texttt{add\_relation}, el grafo se cierra
explícitamente con \texttt{sort\_edges\_by\_timestamp}. Esa función
hace tres cosas: ordena las aristas por
\((\texttt{source\_sid}, \texttt{timestamp})\), marca el grafo como
\emph{sealed}, y reinicializa los \texttt{OnceLock} de los índices
auxiliares (NLF, k-hop) para que se construyan \emph{lazy} en el
primer hunt. Sin esa finalización, el matcher no puede hacer
búsqueda binaria sobre las aristas; con ella, los hunts vuelan. El
truco del \emph{lazy build} es lo que destrabó el caso ``28~GB de
EVTX'': antes, finalizar duraba 1--3~minutos (índices construidos
\emph{eagerly}); ahora termina apenas el merge sort, los índices se
posponen al primer hunt.
\end{intuicion}

\section{Por qué hace falta finalizar}

Durante la ingesta, \texttt{add\_relation} hace \texttt{push\_to\_streaming}
al \emph{streaming backend} en orden de llegada. Las aristas
\emph{no} están sorted por \texttt{timestamp} per-vertex; pueden venir
mezcladas:

\begin{lstlisting}
[ (alice@db01, t=10),
  (bob@web02, t=11),
  (alice@web02, t=12),
  (alice@db01, t=13),
  ... ]
\end{lstlisting}

\noindent
El matcher quiere preguntar ``los vecinos salientes de \texttt{alice}
en \([t_{\mathrm{lo}}, t_{\mathrm{hi}})\)''. Sin orden,
responder esa pregunta requeriría escanear todas las aristas
($O(m)$) ---inviable para $m = 10^8$. Con orden, es búsqueda
binaria sobre un slice ($O(\log m)$ + tamaño del sub-slice).

\section{La operación \texttt{sort\_edges\_by\_timestamp}}

\begin{lstlisting}[language=Rust]
pub fn sort_edges_by_timestamp(&mut self) -> Result<(), Error> {
    self.streaming.finalize();            // per-vertex sort
    self.edges_sorted = true;
    self.nlf = OnceLock::new();           // reset lazy index
    self.khop_reach = OnceLock::new();
    Ok(())
}
\end{lstlisting}

\noindent
Tres pasos: sort per-vertex, marcar sealed, reinicializar índices.
Cada uno tiene su matiz.

\subsection{Paso 1: sort per-vertex}

El \texttt{streaming.finalize()} (capítulo~\ref{cap:streaming-mirror})
hace:

\begin{enumerate}
    \item Para cada vértice (\texttt{Inline} o \texttt{Vec}):
    \texttt{sort\_unstable\_by\_key(|e| e.timestamp)}.
    \item Para vértices ya \texttt{Mmap}-spilled: skip ---ya están
    sorted por construcción (auto-spill sortea durante el write).
\end{enumerate}

\noindent
El sort es la operación cara. Para $10^8$ elementos de 32~B, un
\texttt{sort\_by\_key} radix-friendly toma $\sim$10 segundos en
hardware típico ($\sim$10~M elementos/seg). Ése es el costo
unavoidable de finalizar; sin él, ninguna búsqueda binaria
funciona.

\subsection{Paso 2: \texttt{edges\_sorted = true}}

Un flag boolean que marca el grafo como sealed. Después de esto,
cualquier \texttt{add\_relation} adicional se rechaza (o, en stage
2a, dispara la \emph{streaming} side ---ver capítulo
\ref{cap:incremental-nlf}).

\subsection{Paso 3: reset de \texttt{OnceLock} para lazy build}

\begin{lstlisting}[language=Rust]
pub struct GraphHunter {
    streaming: Arc<InMemoryStreamingBackend>,
    edges_sorted: bool,
    nlf: OnceLock<NlfTable>,
    khop_reach: OnceLock<KHopReach>,
    // ...
}
\end{lstlisting}

\noindent
\texttt{OnceLock<T>} es una primitiva de la stdlib de Rust que
permite construir un valor \emph{como mucho una vez}, en forma
\emph{lazy} y \emph{thread-safe}. La primera llamada a
\texttt{ensure\_nlf()} construye la tabla; las siguientes ven el
resultado sin reconstruir.

\section{Lazy build: el cambio que destrabó 28 GB}

Antes de \emph{heavy-logs \#3.5} (commit del cambio), la
\texttt{sort\_edges\_by\_timestamp} construía NLF y k-hop
\emph{eagerly}:

\begin{lstlisting}[language=Rust]
// Versión vieja (eager)
pub fn sort_edges_by_timestamp(&mut self) -> Result<(), Error> {
    self.streaming.finalize();
    self.edges_sorted = true;
    self.nlf = NlfTable::build(self)?;            // <-- $\sim$30s
    self.khop_reach = KHopReach::build(self)?;    // <-- $\sim$1min
    Ok(())
}
\end{lstlisting}

\noindent
Para 28~GB de EVTX (200~M aristas): merge sort $\sim$30~s + NLF
build $\sim$30~s + khop build $\sim$1.5~min = ~3 minutos. La UI
quedaba \emph{frozen} mientras el motor procesaba; el usuario veía
un spinner sin feedback de progreso.

\subsection{La nueva versión}

\begin{lstlisting}[language=Rust]
// Versión nueva (lazy)
pub fn sort_edges_by_timestamp(&mut self) -> Result<(), Error> {
    self.streaming.finalize();
    self.edges_sorted = true;
    self.nlf = OnceLock::new();         // diferido
    self.khop_reach = OnceLock::new();  // diferido
    Ok(())
}

pub fn ensure_nlf(&self) -> &NlfTable {
    self.nlf.get_or_init(|| NlfTable::build(self))
}

pub fn ensure_khop_reach(&self) -> &KHopReach {
    self.khop_reach.get_or_init(|| KHopReach::build(self))
}
\end{lstlisting}

\noindent
Ahora \texttt{sort\_edges\_by\_timestamp} sólo paga el merge sort
($\sim$30~s para 28~GB). NLF y k-hop se construyen al primer
\emph{hunt} que los consulta:

\begin{itemize}
    \item Hunt sin filtros NLF: nunca llama \texttt{ensure\_nlf()},
    NLF jamás se construye.
    \item Hunt con un solo paso: llama \texttt{ensure\_nlf()},
    paga 30~s una vez, los siguientes hunts encuentran NLF ready.
    \item Hunt multi-hop: llama \texttt{ensure\_khop\_reach()},
    paga 1.5~min una vez, los siguientes hunts encuentran khop
    ready.
\end{itemize}

\noindent
Visible al usuario: abrir una sesión 28~GB es \emph{instantáneo}
(sólo stream binario + merge sort = $\sim$30~s); el primer hunt es
lento (paga el index build); los siguientes vuelan. Si el analista
quiere evitar el primer-hunt-lento, dispara un \emph{warm-up hunt}
trivial apenas carga la sesión.

\subsection{Cómo \texttt{OnceLock} garantiza thread-safety}

\texttt{OnceLock::get\_or\_init} hace internamente:

\begin{enumerate}
    \item \texttt{load} atómico del puntero. Si está inicializado,
    retorna directo.
    \item Si no está, toma un mutex interno (sólo durante la
    inicialización).
    \item Re-chequea el puntero (otro thread pudo haber inicializado
    mientras esperabas el mutex).
    \item Si sigue None, ejecuta el closure, escribe el resultado,
    publica el puntero atómicamente.
    \item Suelta el mutex.
\end{enumerate}

\noindent
Garantía: la inicialización ocurre \emph{exactamente una vez}, sin
importar cuántos threads la disparen. Los lectores subsecuentes
hacen sólo el \texttt{load} atómico ($\sim$5~ns).

\section{Auto-spill por-vértice (cuando no entra en heap)}

Para 200~M aristas el grafo entero no cabe en RAM. El
\emph{streaming backend} cae a \emph{auto-spill incremental}:

\begin{enumerate}
    \item Track de \texttt{edges\_since\_last\_spill}; cuando cruza
    el \emph{budget} (default $10^6$ aristas) dispara
    \texttt{auto\_spill()}.
    \item Cada round: para cada vértice, sortear su slice por
    \texttt{timestamp} \emph{durante el write} (slice ya sorted vía
    \texttt{sort\_unstable\_by\_key}).
    \item Escribir un archivo \emph{round-numbered} con header,
    offset table per-vertex, y la región de datos contiguous
    de \texttt{StreamEdge}s.
    \item \texttt{mmap} el archivo y swap-ear cada
    \texttt{NeighborList} a la variante \texttt{Mmap \{ handle,
    byte\_offset, len \}}.
    \item Borrar el archivo del round previo (\emph{Arc count} cae
    a 0 cuando todos los slots se reemplazan).
\end{enumerate}

\noindent
Costo per-round: $O(V_{round} \log V_{round} + E_{round})$
comparaciones más $E_{round} \cdot 32$~B de I/O. Para
$E = 2 \cdot 10^8$ con budget $10^6$ son $\sim$200 rounds; cada uno
escribe $\sim$32~MB. En SSD NVMe (1~GB/s) cada round toma
$\sim$30~ms; total amortizado $\sim$6~s a través de toda la
ingesta.

\section{¿Por qué sort por (source\_sid, timestamp) y no
(timestamp, source\_sid)?}

El matcher pide \emph{primero} ``los vecinos de un vértice''
(\texttt{neighbors\_of(sid)}) y \emph{después} restringe por
ventana temporal. Sortar por \texttt{source\_sid} primero permite
que cada \texttt{neighbors\_of} devuelva un slice contiguo
(amigable con cache). Sortar por \texttt{timestamp} primero haría
que los vecinos de un vértice estén dispersos por todo el array
---inservible.

\begin{nota}
Dentro del slice de un \texttt{source\_sid}, las aristas están
ordenadas por \texttt{timestamp} secundario, lo que permite la
segunda búsqueda binaria por ventana temporal. La elección
\((\texttt{source\_sid}, \texttt{timestamp})\) es lexicográfica y
óptima para el patrón de acceso del matcher.
\end{nota}

\section{Resumen}

\begin{itemize}
    \item \texttt{sort\_edges\_by\_timestamp} es la finalización del
    grafo. Ordena aristas, marca sealed, resetea índices.
    \item Sort interno via \texttt{sort\_by\_key} en RAM, o merge
    sort multi-archivo cuando excede budget.
    \item Lazy build: NLF y k-hop se construyen al primer hunt que
    los consulta, no al finalizar. Destrabó el caso 28~GB.
    \item \texttt{OnceLock} garantiza inicialización exactamente-una
    bajo concurrencia; sin double init, sin tornados.
    \item Sort key es \((\texttt{source\_sid}, \texttt{timestamp})\)
    para que \texttt{neighbors\_of} + búsqueda binaria por ventana
    den slice contiguo.
\end{itemize}

\begin{enumerate}
    \item \starred{} Para una sesión de $5 \cdot 10^7$ aristas que
    cabe entera en heap ($1.6$~GB), ¿cuánto tarda
    \texttt{sort\_edges\_by\_timestamp} con la versión nueva
    (lazy)? ¿Cuánto tardaba con la vieja (eager) si NLF construye en
    $\sim$15~s y khop en $\sim$45~s?

    \item ¿Por qué \texttt{OnceLock::new()} y no
    \texttt{drop(self.nlf)} para resetear? Pensá la diferencia
    semántica.

    \item \starred{} Diseñá una métrica que el motor pueda exponer
    al usuario para dar feedback durante el merge sort. ¿Es viable
    sin frenar el sort?

    \item ¿Por qué la decisión ``sort por (source\_sid, timestamp)''
    es lo correcto para subgraph matching? Discutí: ¿qué pasa si
    cambiamos a (timestamp, source\_sid)? ¿Para qué tipo de hunt
    sería mejor?

    \item Imaginá un usuario que dispara 100 hunts secuencialmente
    sobre el mismo grafo. ¿Cuántas veces se construye NLF? ¿Y
    khop? ¿Cuál es el costo amortizado por hunt si el primer hunt
    paga 30~s + 1.5~min?
\end{enumerate}
\end{ejercicios}
